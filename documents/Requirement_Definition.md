# Loopworks 要件定義

## 1. 一言サービスコンセプト

回収・加工・売却まで、現場での一度の入力で記録に残せるアプリ。

## 2. 誰のどんな課題を解決するのか？

廃品回収・スクラップ加工を営む企業の、現場作業員と事務スタッフが対象。

- 現場作業員は、切断した品目と重量を紙の台帳に書き込んでいる。出荷や売却のたびに、品目ごとに重量を手で足し合わせて計算しており、種類の書き方や順番がバラバラなので毎回時間がかかり、足し間違いも起きやすい。
- 事務スタッフは、紙の台帳に書かれた記録を、集計のために後からExcelに転記している。紙とExcelの二重管理になっていて手間がかかるうえ、転記ミスも起きやすい。
- 売却額は、売却先(買主)が提示する金額をそのまま受け入れる形になっている。自社側で「だいたいいくらになるはずか」を売却前に確認する手段がなく、提示された金額が妥当かどうかを判断する材料がない。

## 3. なぜそれを解決したいのか？

友人が勤務する会社が今もアナログな紙管理で苦労しているのを知り、現在学んでいるRailsやSQL、これまでのキャリアで培ったマーケティング・業務改善の視点を、実際に困っている人のために使ってみたいと思ったため。学習の成果を「誰かに実際に使われるもの」として形にしたいという思いが、開発を最後までやり切る原動力になっている。

## 4. どうやって解決するのか？

紙の台帳に書いていた生産記録を、現場の端末からその場でまとめて入力できるようにし、品目・等級・回収元ごとに自動で集計・累計を出す。売却時には実際の売却額を別途記録し、想定額(記録時点の単価から算出した見積額)との差を比較できるようにする。

AIは「正確な値を新しく作る」場面では使わず、入力したデータの異常を知らせる場面に限定して使う。

## 5. 機能要件

### 5-1. ユーザー・権限

- ログイン機能（社員番号＋パスワードなど、シンプルな方式を想定）
- ロールは `admin` / `staff` の2種類
  - `admin`：品目・等級・回収元・売却先マスタの追加編集削除、単価・税率の変更、生産記録・売却記録の削除、金額の閲覧
  - `staff`：生産記録の入力・閲覧のみ(重量ベース、金額は非表示)、削除不可

### 5-2. マスタ管理（品目・等級・回収元・売却先）

- 品目マスタ：品目名、現在の単価。使用中（生産記録・売却記録から参照されている）品目は削除不可。
- 等級マスタ：等級名（例：A級・B級・並）。品目×等級ごとに単価を持つ想定（友人へのヒアリングにより、掛け率方式に変更する可能性あり）。
- 回収元マスタ：回収してくる取引先の一覧。使用中は削除不可。
- 売却先マスタ：スクラップを売却する回収業者の一覧。回収元とは別マスタとして管理。使用中は削除不可。
- 単価・税率の変更履歴ログ：いつ・誰が・いくらに変更したかを記録する。

### 5-3. 生産記録

- 日付・品目・等級(任意)・回収元(任意)・重量を、1回の操作で複数品目まとめて入力できる。
- 記録時点の単価・税率をスナップショットして保存し、後からマスタの単価を変更しても過去の記録の金額は変わらない。
- 入力するたびに、品目別の累計重量が自動で積み上がって表示される（台帳のように記録が積み重なるイメージ）。
- 自由記述のメモ欄を持つ。
- 写真を1枚添付できる(Active Storageを利用、AIによる画像解析は行わない)。
- 重量の入力に範囲チェックを設け、0以下や極端に大きい値を防ぐ。
- 削除は論理削除とし、誤操作時にも復旧できるようにする。

### 5-4. 売却記録

- 日付・売却先・品目・重量・実際の売却金額を手入力で記録する。
- CSVインポートは行わない(友人から正式なフォーマットを得られる見込みが薄く、人が記憶を頼りに入力する以上、フォームへの直接入力と実質的に変わらないため)。
- 記録済みのデータはCSV出力でき、Excelで開いて税理士への共有や帳簿への反映に使える(仕訳や税区分の判定など、会計ソフト的な機能は持たない)。

### 5-5. 検索・集計・出力

- 生産記録を日付の範囲・品目で検索・絞り込みできる。
- 生産記録・売却記録をCSVで出力できる(UTF-8・Shift-JISの両方の文字コードに対応する)。
- 品目別合計を、今月と前月で並べて比較表示できる。
- 1日分の品目別合計を1枚に収めた、出荷サマリーの印刷用ビューを持つ。

### 5-6. AI補助機能

- 異常値検知：品目ごとに直近の記録から平均重量を算出し、新しい入力が平均から大きく外れていた場合、保存前に確認ダイアログを表示する(ブロックはせず、再確認を促すのみ)。

## 6. 非機能要件

- ユーザビリティ：使用者の年齢層が高いことを想定し、フォント・ボタンを大きく、配色はハイコントラストにし、少ないタップ数で操作が完結するようにする。iPad・スマホでも操作しやすいレスポンシブUIとする。
- データ整合性：単価・税率は記録時点の値をスナップショットして保持し、マスタの変更が過去の記録に影響しないようにする。削除は原則として論理削除とする。
- セキュリティ・権限：ログインを必須とし、`admin` / `staff` のロールによって閲覧・操作できる範囲を分離する。
- 運用環境：ローカル環境(DBサーバー不要な構成)でも動作可能とし、必要であれば同一LAN内の複数端末からアクセスできる構成も後から選択できるようにする。
- 互換性：CSVの入出力において、UTF-8・Shift-JISの両方の文字コードに対応する。


## 今後ヒアリングが必要な事項

- 等級による単価の違いが、品目ごとの個別単価か、掛け率のような仕組みかどうか。
- 回収時にお金が動くか（買い取り／処分費としての収入／無料）。品目によって異なるかどうか。
- 給与計算の際、売上やコストの数字を現在どこから出しているか（既存のExcel・ノートの有無の確認）。
- 入力する人数・端末数(事務所のPCからも生産記録を同時に見たいかどうか)。
